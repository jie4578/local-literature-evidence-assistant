# Grounded Evidence Q&A Core

## Implemented

- `EvidencePack` is built only from the existing current-batch retrieval response.
- The program assigns deterministic `E1`, `E2`, … IDs after retrieval.
- Evidence is capped at 8 passages, 1,200 characters per passage, and 8,000
  provider-input characters by default. Original passage text and metadata remain
  available to the local renderer; only the provider payload is bounded.
- `GroundedAnswer` accepts only structured claims linked to known evidence IDs.
- Unknown or missing citations are removed; no provider-supplied filename,
  section, or page is trusted.
- The renderer fills source file, section, and physical PDF page from the
  `EvidencePack`, including multi-page ranges.
- Empty retrieval deterministically abstains without creating or calling a
  Provider.
- The UI exposes `Evidence Only` by default. It shows retrieved source text and
  does not generate a natural-language conclusion.
- Provider-grounded answering is implemented as a dependency-injected,
  mock-testable core, but it is not enabled in the UI in this phase.

## Safety boundary

Evidence is sent to an optional Provider only as explicitly selected, bounded,
quoted data. It is marked as untrusted source material, and prompt-like text
inside it must not be followed. Questions are not persisted to SQLite,
manifests, status files, logs, or output artifacts.

`citation validated` means only that an evidence ID exists in the current
EvidencePack and that its source/page metadata was programmatically bound. It
does not mean that a scientific claim is true, peer-reviewed, replicated,
clinically valid, or semantically entailed.

## Not yet validated

- Real Provider grounded Q&A.
- Semantic entailment correctness.
- Scientific truth or clinical validity.
- Validation on a real biomedical corpus.

## Schema compatibility investigation

The previous Test A run established only that JSON parsing succeeded, two
claims and two evidence-ID lists were observed, and zero claims survived final
validation. The raw Provider response was not persisted, so the exact
historical mismatch remains `UNKNOWN_FROM_PREVIOUS_RUN`.

The current canonical contract is:

```json
{
  "status": "supported" | "insufficient_evidence",
  "claims": [{"text": "string", "evidence_ids": ["string", "..."]}],
  "limitations": ["string", "..."]
}
```

The diagnostic stages are separated as `parse_status`,
`top_level_schema_status`, `claim_schema_status`, `citation_status`,
`status_consistency_status`, and `final_validation_status`. Structural
fingerprints contain types, key names, counts, and boolean checks only; they do
not contain claim text, evidence text, raw responses, secrets, questions, or
paths.

Security-critical rules remain strict: evidence IDs must exist, must come from
the current EvidencePack, and model-controlled source/page/section metadata is
never authoritative. Malformed JSON cannot fall back to free text. The
compatibility layer applies only two conservative mappings after JSON parsing
and before strict validation: an exact string `claim` field may map to `text`
when `text` is absent, and a non-empty string `limitations` value may become a
one-item list. Both mappings preserve the original string exactly. Conflicts,
non-string aliases, empty limitation strings, non-string limitation items,
unknown fields, status casing, evidence-ID shape, and provider citation
metadata remain strict failures. No citation, page, source, section, or claim
semantic rewrite is performed.

Normalization diagnostics contain only applied rule names, safe structural
fingerprints, warnings, and conflicts; they do not persist response values,
secrets, prompts, paths, or raw Provider output. The synthetic fixture
`LIVE_OBSERVED_SHAPE_V1` is explicitly reconstructed from a safe diagnostic
shape and is not claimed to be a raw Provider replay.

The Provider abstraction currently exposes a prompt/schema argument but does
not add a Provider-specific JSON response-format mode; structured-output
enforcement is therefore `PROMPT_ONLY`.
